# LLM Image Lens

A source-bound video inspection CLI for an LLM: locate shot boundaries, request a small original-frame contact, and read conservative 2D surface-motion reports. The bounded improvement in this release is a compact shot brief/catalog, with native frame/PTS ranges, source hashes, missing coverage and exact raw-artifact locators. No pose, action, identity or easing accuracy improvement is claimed.

Core workflows retain the selected existing engines: diagnostic frame comparison, canonical full-source hard-cut context, surface-point timing, explicit actor/feature reports, source-color regions, and optional flat-background foreground inspection. Default image output is **zero**. Explicit source contacts share an eight-frame cap; comparison uses two originals and one derived residual panel.

## Run without installing

Requires Python 3.11+ for stdlib commands. Decode/render commands additionally need `requirements.txt`; dependencies, checkpoints and media are not bundled. Python 3.12 on macOS arm64 is the verified extraction environment. Windows core operation and installed-wheel execution remain unverified; experimental tracking requires a POSIX parent watchdog.

From the repository:

```sh
python -m image_lens --help
python -m image_lens --workspace /path/to/workspace scan --video input.mp4 --out shots.json
python -m image_lens --workspace /path/to/workspace brief --shots shots.json --out brief.json
python -m image_lens --workspace /path/to/workspace catalog --shots shots.json --offset 0 --limit 8 --format markdown --out brief.md
python -m image_lens --workspace /path/to/workspace compare --shots shots.json --frames 5,6 --evidence-dir comparison --out comparison.json
```

From a different working directory, including isolated Python, use the absolute path to the thin direct launcher:

```sh
python -I /path/to/llm_image_lens/image_lens_cli.py --workspace /path/to/workspace brief --shots shots.json --out brief.json
```

An optional installation exposes `image-lens`; extras are `.[core]`, `.[tracking]` and `.[pose]`. A stdlib-only installation has no mandatory runtime dependencies. Pinned PySceneDetect source is already vendored. The public CLI is the supported entrypoint; individual engine mains are internal adapters.

All relative data/output paths are relative to the selected workspace, default `<repository>/workspace`. Source inputs must be copied there explicitly. Inputs and outputs cannot escape this boundary; symlink components and overwrites are refused. The optional checkpoint is the sole explicit external input exception. Workspaces, videos, models, generated images and results are Git-ignored.

## Read the brief

`brief` and `catalog` emit the same bounded schema, `image-lens.brief/1`. Eight shot rows are returned by default (maximum 16); `next_offset` and omitted counts make pagination explicit. Native PTS arrays stay at the raw scan locator. Source bytes and current detector helper/source pins must match before a verified brief is issued. Partial-source scans remain explicitly partial; incomplete decode packets are rejected. Hash checks bind bytes and provenance, not the correctness of detected cuts.

An optional `--report report.json` adds only supported cached motion reports that can be recomputed from their pinned source tracks and bindings under the exact canonical scan. Missing, outdated, unsupported or cross-cut reports are listed as `not_admitted`; their coverage remains unknown. Eight report references maximum. No LLM/API call, network, image generation, raw-coordinate dump or model import is performed by a brief. Labels in reports are untrusted quoted data.

Every shot retains its fresh-source-observation/retracking obligation. A single-frame shot permits inspection only. A missed cut or dissolve is possible; no detected cut does not prove continuity or identity. Do not crop coordinates from a whole-clip offline inference and call them shot-local tracking.

## Fresh jobs and optional tracking

See [the job contract](docs/jobs.md). `prepare` accepts a fresh query packet and canonical full-source scan, validates one shot-local job, and creates a new immutable freeze. Its default permits validation only. `validate` checks source bytes, queries, vendor/helper pins, decode/PTS and cuts **without importing Torch**, without a checkpoint and without producing tracks. It requires the core decode dependencies.

```sh
python -m image_lens --workspace /path/to/workspace prepare --queries queries.json --shots shots.json --job shot0 --out job.freeze.json
python -m image_lens --workspace /path/to/workspace validate --queries queries.json --frozen job.freeze.json --job shot0 --out unused-tracks.json
```

Experimental inference requires a separately prepared freeze with `--allow-tracking`, an explicit local checkpoint and a frozen wall budget. Its single attempt is consumed immediately before the model import; failures never trigger automatic retries. The CLI parent kills/reaps its own child process group if the budget expires. No download occurs. CoTracker source and checkpoint have noncommercial upstream terms. No neural inference was run to validate this extraction.

```sh
python -m image_lens --workspace /path/to/workspace prepare --queries queries.json --shots shots.json --job shot0 --allow-tracking --max-seconds 120 --out tracking.freeze.json
python -m image_lens --workspace /path/to/workspace track --queries queries.json --frozen tracking.freeze.json --job shot0 --max-seconds 120 --checkpoint /path/to/scaled_offline.pth --out tracks.json
```

For observed-surface tracks, selected analysis is available through the real engine:

```sh
python -m image_lens --workspace /path/to/workspace analyze --tracks tracks.json --shots shots.json --point surface0 --start 0 --end 30 --out timing.json
python -m image_lens analyze --help
```

For an LLM reader, add `--report-bindings bindings.json --format markdown --trajectory-dir traj` to a report. The Markdown then leads with coarse strokes (median-filtered path split at corners and pauses, major = at least half the largest unit), and `traj/trajectory.png` shows the whole-frame path (blue early, red late), a stroke/timeline strip and up to four uncropped frames. The same pass lists appearance-change candidates: consecutive-frame gray-difference jumps to check with `compare --frames a,b`. A major stroke that overlaps a candidate is flagged, because echo/redraw can make the point jump. Strokes are recomputed in `brief`; the picture and candidates are not.

## One command: look

`look` runs the steps below in order and writes everything into one new directory: `scan`, one `pose` pass, then for each shot (first 16 by default, `--max-shots` up to 256) pose-seeded `seed`/`prepare`/`track`/`bind`/`analyze` per group and per window. Shots longer than 160 frames are split into consecutive windows, each reseeded on its first unflagged pose frame. Single-frame shots, shots without a usable pose track and short tails are skipped with a reason. A failed step is recorded and the next job continues; `--max-seconds` is checked between steps (each step keeps its own budget), so a run can overshoot by one step. Read `look.md` first: one line per tracking window (AKAGE: 55 lines instead of 542). The whole-frame and body-centre shifts are said once ("전체"), then what the limbs did on top of them ("몸 기준"; points of one screen-side arm or leg whose first stroke has the same direction and a size within half of each other are one statement, largest three shown, the rest counted), the per-height flow and notes (drawing change, lost points, warnings). When the skeleton is implausible the line lists the largest screen moves instead. A drawing swap gets a "전환" line: the pose difference between the two frames; the path between them is not observed. Repeated poses are written once: when a window's first and last frames (person box, 24×24 grey) both match an earlier window's at correlation 0.9 or more and its length is within 80%, it is the same pose shown again ("자세 A"; AKAGE groups into its four costumes plus the long black-dress hold, while different poses stay at 0.48 or below; no MikuMiku cover is merged). `look.md` lists the repeated poses first, gives the first showing in full and each repeat only what differs (statements matched by direction and size within 8 px or a quarter, whatever their label, because move-point letters are per window and the pose model sometimes names the other arm on identical drawings). A switch between two poses already seen in that order says so instead of repeating the numbers. The detailed text (major moves per group, "moved together" lines, warning counts, paths to the full report and trajectory sheet) is `look-full.md`; `focus --look <dir> --shot shot-0007` prints one shot of it as plain Markdown. When at least half of one group's points stop more than 12 frames before the window ends, `look` treats it as a drawing change (on AKAGE every such case was a costume change or a wipe inside one detected shot): the window is analyzed only up to that frame and a new window is reseeded from pose right after it. A group that still loses most of its points gets a line "f<N> 뒤로 점 k/n개 끊김"; read what follows as unknown, not still. Each window also gets a body-relative block: limb points (wrists, elbows, thumb and index tips, thighs, knees, ankles) are measured against the shoulder midpoint (or the face when shoulders are missing), the body centre's own shift gets its own line, paths are split where they turn ("아래 → 위"), and "몸 쪽으로/바깥으로" is the change in distance from the body axis. The threshold is 6% of shoulder width (8 px minimum), and sides are screen sides taken from the limb's shoulder or hip. Hand tips come from the pose model's hand keypoints and are rough on drawn hands; thighs sit halfway from hip to knee, so legs cut off by the frame still get a point. When a window starts within 3 frames of the previous one (a costume change or a cut between two shots of the same figure), a "전환 앞뒤 자세 차이" block compares wrist and elbow pose keypoints on the two frames, body-relative. Animated moves often run through the drawing swap (an arm dropping from the side to the waist on the switch frame), which no single window can see. It is skipped when the shoulder width changes by more than a third or the body centre jumps more than one shoulder width. Before naming arm and leg points, `seed` checks the pose skeleton (core joint scores, torso length, hip width and arm segments in shoulder widths). When it is implausible (props, costumes or odd poses fool the pose model), only the face is named; `look.md` says "골격 신뢰 낮음" and skips the body-relative block. Each window line also names the shot framing from the seed pose: 전신 (both ankles scored 0.6 or more and at least two shoulder widths below the shoulders), 무릎 위 (hips pass the full check, feet out of the shot; all of AKAGE), 얼굴 클로즈업 (eyes 30% of the frame width apart or more, or no shoulder seen) or 상반신. On upper-body shots the pose model guesses hips onto the chest and ankles at the frame bottom (Seedance: 37 of 43 windows were face-only); there the arms are named from both shoulders alone when every seen arm joint passes the same score and segment limits, the legs are left out and the line says "(팔만)". Every window also gets "많이 움직인 곳" points (`move-a`…): the seed frame is compared with the frames at one third, two thirds and the end (before any drawing swap, camera shift removed), and up to 12 candidates go where the onion gaps are widest on an outline of the seed frame. All candidates are tracked; candidates whose tracked paths stay within 16 px or half the larger travel are one moving part and keep one point, and parts travelling under 40% of the farthest are dropped, so an arm-only move gets one point (six at most). Only those points reach the report (`<window>-move-parts.bindings.json`); every candidate stays in the tracks file. Gap width alone misleads: in the MikuMiku hammer scene the widest gap moved 39 px while the hammer moved 450 px. A gap on empty start-frame background is where a part arrives and gets no point. Whole-frame motion (camera pan or zoom, scrolling UI) is estimated per window from ORB matches against the seed frame; it counts only when the agreeing matches span at least half the width and a quarter of the height, so a large figure sliding over a still layout is not mistaken for the camera. When it moves 24 px or more, a "화면 전체" line reports it and major moves that only follow it are dropped. Each window also gets a "높이별 흐름" line: the person box is split into five horizontal bands, corner features in each band are followed from the first to the last frame, and the median shift per band (minus the camera) is reported. It needs no named points, so a hip pushed out under a skirt or a prop shows up (AKAGE pose 1: head right ~22 px, waist and skirt left ~20–29 px; the three repeats agree within 5 px). The onion image `<window>-onion.jpg` overlays the first frame in cyan and the last in red, with the band shifts as arrows (×2). All onion images of a run are also laid out with their time ranges on `onion-sheet-N.jpg` (16 per sheet), so an image-reading agent can see gestures the text loses (heart hands, V signs): on the Seedance clip a blind reader scored 5/21 of the user's moves from `look.md` alone and 9/21 with the sheets. A range too short to track (under 12 frames) gets one native still of its middle frame on the sheets, labelled "still" (pose only, motion unknown); stills of back-to-back cuts share one row in time order: on Seedance the spin at 1.8–2.2 s is seven cuts of 3–6 frames and was invisible until these stills. Each onion image also gets a grey panel on its right: the frame most unlike the first, searched away from both ends (middle of the plateau of mean grey difference), so a move that goes out and comes back is not read as still. From the per-frame pose `look` also writes hand-near-face runs (wrist seen and a hand point inside the face box padded by a quarter of its width for 0.1 s or more, with the region 이마·눈/볼/입·턱; noisy: on Seedance a cat's paws and chin-height hands count too), each shoulder's rises and falls above the hips (or the eyes) in shoulder widths, and shoulder-width changes against the eye distance. A width swing of 35% or more is said as "몸 돌림 후보" and the shoulder heights are dropped, since the points jump during a turn. A wrist seen in under half the window is said as "대부분 안 보임: 멈춤 아님, 모름". After these changes a fresh reader scored 12.5/21 on the same clip; that is a check that the changes reach the reader, not a blind score, because they were made after seeing the key. Pose events follow the seed person's tracker id only; frames where that id is missing are counted ("포즈 추적이 N프레임 끊김: 그동안 모름") instead of taking another detection. A hand near the face is said as already near at the start or coming in, and as moving away or staying to the end. Only shoulder heights that overlap a turn candidate are dropped. The six windows with the largest shoulder-width swing also get a strip of five frames in time order (evenly spaced, the far frame in place of its nearest) as their own row on the sheets; giving one to all 18 turn candidates doubled the sheets (8 to 14) for about the same fresh-reader score (13 vs 12.5 of 21, one reader each, not blind). Windows with several people (present in half the window or more, at least a quarter of the largest one's box area; up to three, named P1… from screen left by tracker id) get a "사람 N명" field: each person's body-centre shift in shoulder widths (camera removed), a fall candidate (torso from 30° or less to 60° or more off vertical), and per pair distance change, a wrist inside the other's shoulder-to-hip box ("닿음 후보") and heavy box overlap ("포즈가 섞였을 수 있음"); a "who" picture with the P boxes goes on the sheets. On the held-out Kaguya live clip (40–70 s, key given after the answers were frozen) the fresh readers scored 2.5/20 from `look.md` alone and 8.5/20 with the sheets; with the people fields 8/20 (not blind any more), so no gain shown: the pull-and-fall shot is one merged detection box. `zoom --video <clip> --out <dir> --at 18-22 [--at a-b]` is a second read: dense whole frames (12 per span, at most two spans of 4 s) on one sheet per span, with the frame and pixel cost in `zoom.json`; `--even` spreads the same 24 frames over the whole clip as a control. On the Kaguya clip (recheck, key known) a reader that chose its own spans went from 10.5 to 11.5 of 20, while a reader given the 24 even frames went from 8.5 to 12: readers do not pick the spans they got wrong (the pull-and-fall at 18–22 s was written confidently as an arm around the shoulder and not chosen). So `look` also writes `frame-sheet-N.jpg`: whole frames every 1.25 s over the whole clip (12 per sheet, at most 96 frames), listed in `look.md` and `look.json` (`frame_sheets`); on the Kaguya clip that is the same 24 frames. `look.json` holds the same record, `steps.log` every step receipt. Each major move also carries its timing (완급) from progress along the move in thirds of its time: 빨라짐 (speeds up), 느려짐 (slows down), 천천히-빠르게-천천히 (fast middle) or 일정 (even).

Where pose seeds fail (props, odd poses, unnamed points), an agent can place and name points itself:

```bash
python -m image_lens --workspace W grid --video V --frame 572 --box 100,250,1000,1000 --out W/grid-f572.jpg
python -m image_lens --workspace W mark --video V --shots W/look/shots.json --frame 572 --end 599 --point hammer-stripe=430,680 --point eye=322,738 --checkpoint C --out W/mark-s19
```

`grid` draws a labelled source-pixel grid (50 px in a zoom box, 100 px otherwise) to read positions from. `mark` moves each given point to the nearest trackable corner within 15 px (`--no-snap` keeps it), writes marked crops as evidence, tracks with the same engine and writes `mark.md` (major moves, every move with timing) plus per-frame coordinates in `mark.tracks.json`. Names are ASCII, up to 8 points, and are the agent's reading, not verified anatomy. On the MikuMiku hammer shot, two points on the hammer head followed the whole swing (wind-up left 74 px, then right and down ~800 px speeding up, settling while slowing) and the eye stayed on the face; a point on the hammer's corner slid onto the hat, and one on the hand stayed behind when the drawing swapped hands.

```sh
python -m image_lens --workspace W look --video clip.mp4 --detector D.onnx --pose-model P.onnx --checkpoint scaled_offline.pth --out look-clip
```

Model paths left out on the command line (`look`, `pose`, `mark`) are read from `<workspace>/models.json`, e.g. `{"detector": "/models/yolox_humanart.onnx", "pose_model": "/models/rtmw133.onnx", "checkpoint": "/models/scaled_offline.pth"}`; a flag given on the command line wins. The workspace is Git-ignored, so each machine keeps its own. With it, `python -m image_lens --workspace W look --video clip.mp4 --out look-clip` is the whole command. A source larger than 1920×1080 (the point tracker's cap) is first shrunk into `source-<w>x<h>.mp4` in the output directory, keeping its aspect; px in the reports are then of that copy.

## Whole-body seeds from pose (optional)

`pose` runs a local whole-body pose model over the canonical scan: YOLOX HumanArt person boxes, RTMW 133 keypoints (rtmlib, ONNX Runtime CPU) and ByteTrack IDs reset at every detected cut. The two ONNX files are user-supplied and pinned by size and SHA256; nothing is downloaded or bundled, and the weight license is not established. Install `requirements-pose.txt` into the same environment. The packet also flags frames where the pose layer itself is unreliable: overlapping person boxes (echo copies, afterimages) and body-skeleton jumps within one track.

`seed` turns one frame of that packet into fresh observation jobs, one per group so each fits the 12-point surface contract: `<job>-head` (nose, eyes, front/top/side hair), `<job>-arms` and `<job>-legs`. Hair points are geometry on a head frame built from the eyes (distance and the up direction away from the nose), so they are candidate surface points, not detected hair. Joints near the frame edge are dropped because off-screen joints come back clamped there. Each seed gets a marked source crop as its pinned visual reference; look at them before tracking. `bind` writes the report bindings for one tracked job.

```sh
python -m image_lens --workspace W pose --shots shots.json --detector /models/yolox_humanart.onnx --pose-model /models/rtmw133.onnx --out pose.json
python -m image_lens --workspace W seed --pose pose.json --frame 215 --job s7 --out s7.obs.json --evidence-dir s7-crops
# prepare/track each of s7-head, s7-arms, s7-legs, then:
python -m image_lens --workspace W bind --queries s7.obs.json --tracks s7-head.tracks.json --job s7-head --out s7-head.bindings.json
python -m image_lens --workspace W analyze --tracks s7-head.tracks.json --shots shots.json --report-bindings s7-head.bindings.json --start 215 --end 307 --format markdown --trajectory-dir s7-head-traj --pose pose.json --out s7-head.md
```

With `--pose`, the trajectory view marks pose-trouble frames (orange on the timeline), tags change candidates near them, and groups warnings so one line names every big stroke that coincides with a candidate or a pose-trouble range. With more than two points, only major strokes are labelled, and the Markdown leads with a one-line-per-point summary plus "moved together" lines (major strokes of several points with the same direction, overlapping time and similar size); per-point speed windows, phases and span comparisons stay in the JSON. Pupils are not modelled; eye points follow the drawn eye area.

Analysis help also exposes review selection, explicit feature bindings, source-color region reports and optional foreground inspection. Read [limitations](docs/limitations.md) before interpretation.
